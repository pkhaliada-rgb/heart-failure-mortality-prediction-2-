A complete machine learning project: exploratory analysis and model comparison in a notebook, a reusable training pipeline, and a local web dashboard for live, per-patient mortality risk predictions.

Predicts whether a heart failure patient is likely to survive or die during their follow-up period, using 12 clinical features recorded at diagnosis — from the real [Heart Failure Clinical Records dataset](https://archive.ics.uci.edu/dataset/519/heart+failure+clinical+records) (Ahmad et al., 2017; 299 patients).

### Dashboard pages

- **Predict** — enter a patient's clinical values and get a mortality risk prediction
- **Model Performance** — accuracy, precision, recall, F1, ROC-AUC, confusion matrix, ROC curve, and feature importance
- **Data Charts** — class balance, key features by outcome, and the full correlation matrix for the training dataset

All charts are generated once when the dashboard starts (not on every page view), so navigating between pages is instant.

## Running it

### 1. Train the model

```powershell
python src/train_model.py
```

This downloads and verifies the dataset (cached in `data/` after the first run), trains a Random Forest classifier, prints its test-set performance, and saves the model plus its metadata to `models/`.

### 2. Launch the dashboard

```powershell
python dashboard/app.py
```

Open `http://127.0.0.1:5000` in your browser. The form comes pre-filled with the training data's average patient — change any values and click **Predict** to see the estimated mortality risk.

### 3. (Optional) Explore the analysis notebook

```powershell
jupyter notebook notebooks/Heart_Failure_Mortality_Prediction.ipynb
```

Covers exploratory data analysis, a Logistic Regression vs. Random Forest comparison, ROC curves, and feature importance — the full reasoning behind the model choice used in the dashboard.

---

## Verifying it works

1. `python src/train_model.py` should print test metrics ending around **~0.85 accuracy** and **~0.90 ROC-AUC** — if these are wildly different, something changed in the data pipeline.
2. `python dashboard/app.py` should print `Model loaded. Dashboard is ready.` with no errors.
3. On the dashboard, leave the pre-filled average-patient values as-is and click **Predict** — you should get a plausible, moderate-risk result.
4. Set `age` to 80, `ejection_fraction` to 20, `serum_creatinine` to 2.5, and `time` to 10 — you should see a clearly **high risk** result.
5. Submit the form with a required field cleared — you should see a friendly "Invalid input" message, not a server error.

## Model details

- **Algorithm:** Random Forest (200 trees, max depth 5), chosen over Logistic Regression after comparison in the notebook (higher accuracy and ROC-AUC on this dataset, no feature scaling required at inference time)
- **Features used:** age, anaemia, creatinine phosphokinase, diabetes, ejection fraction, high blood pressure, platelets, serum creatinine, serum sodium, sex, smoking, follow-up time
- **Target:** `DEATH_EVENT` — whether the patient died during the follow-up period
- **Evaluation:** stratified 80/20 train/test split (the dataset is imbalanced — only ~32% of patients died), evaluated with accuracy, precision, recall, F1, and ROC-AUC rather than accuracy alone

See the notebook for the full comparison against Logistic Regression, correlation analysis, and feature importance breakdown.

## Data source and reliability

The dataset is streamed from a tested GitHub mirror of the original UCI dataset, with a second mirror as backup. If both are unreachable, `src/data_loader.py` prints direct links to the dataset on UCI and Kaggle so it can be downloaded manually and placed in `data/`.

Once downloaded, the dataset is cached locally — `train_model.py` and the notebook will not re-download it on subsequent runs.

## Retraining with different settings

Open `src/train_model.py` and adjust the `RandomForestClassifier` parameters (`n_estimators`, `max_depth`), or the `test_size`/`random_state` in the train/test split, then re-run:

```powershell
python src/train_model.py
```

The dashboard automatically picks up the newly saved model the next time it starts — no code changes needed in `dashboard/app.py`.
